# Capítulo III: Requirements Specification
A partir del análisis de la información obtenida en las investigaciones del Capítulo II, esta sección especifica los requisitos de los productos digitales que componen la solución. Los requisitos se expresan como Epics y User Stories con criterios de aceptación redactados en estructura Gherkin, se vinculan con los objetivos de negocio mediante el Impact Map, y se priorizan en el Product Backlog según el valor que aportan al negocio.

## 3.1. User Stories

Los criterios de aceptación se redactan en tiempo presente y tercera persona, son comprobables y no hacen referencia a detalles de interfaz de usuario. Las únicas excepciones a la estructura Given-When-Then corresponden a reglas de negocio o restricciones que no dependen de condiciones.

Se incluyen User Stories para el sitio web estático tomando como rol base el visitante. Las historias **US43 a US52 son Technical Stories**: su rol base es el de *developer* y corresponden a componentes sin interacción directa con usuarios finales, concretamente el RESTful API, el Edge Service y la aplicación embebida del dispositivo IoT. Se mantienen dentro de la numeración correlativa para que su trazabilidad hacia el Impact Mapping y el Product Backlog sea directa.


### Epics

| Epic ID | Título | Descripción |
|---|---|---|
| **EP01** | **Landing Page y presentación del modelo de negocio** | Como equipo de OsoTerra, deseamos contar con un sitio web estático que presente el modelo de negocio y las características de la solución a los distintos segmentos, para convertir visitantes en usuarios registrados. |
| **EP02** | **Identity and Access Management** | Como equipo de OsoTerra, deseamos gestionar la identidad y los permisos de los usuarios, para garantizar que cada uno acceda únicamente a la información que le corresponde. |
| **EP03** | **Subscriptions and Payments** | Como equipo de OsoTerra, deseamos gestionar los planes de suscripción y su facturación, para sostener la operación del negocio. |
| **EP04** | **Farm and Plot Management** | Como equipo de OsoTerra, deseamos permitir la organización de la información en fincas, parcelas y cultivos, para contextualizar agronómicamente cada medición. |
| **EP05** | **Device Management** | Como equipo de OsoTerra, deseamos gestionar el ciclo de vida de los dispositivos IoT, para asegurar la trazabilidad y la salud del parque instalado. |
| **EP06** | **Soil Monitoring and Telemetry** | Como equipo de OsoTerra, deseamos capturar, validar, compensar y persistir las mediciones del suelo, para constituir la base de información de toda la solución. |
| **EP07** | **Alerting and Notifications** | Como equipo de OsoTerra, deseamos evaluar las mediciones contra los umbrales del cultivo y notificar oportunamente, para que el usuario pueda actuar antes de que el daño se consolide. |
| **EP08** | **Analytics and Reporting** | Como equipo de OsoTerra, deseamos ofrecer visualizaciones y reportes derivados de la información recolectada, para sustentar las decisiones de ambos segmentos. |
| **EP09** | **Advisor Multi-plot Management** | Como equipo de OsoTerra, deseamos dotar al asesor técnico de capacidades de supervisión simultánea, para que pueda atender a más clientes sin incrementar sus desplazamientos. |
| **EP10** | **RESTful API Services** | Como equipo de OsoTerra, deseamos exponer las capacidades de la plataforma mediante un RESTful API documentado y versionado, para que las aplicaciones web, móvil y embebida se integren sobre una única fuente de verdad. |
| **EP11** | **Edge Service and Embedded Application** | Como equipo de OsoTerra, deseamos disponer de un servicio de borde y una aplicación embebida que capturen, validen y sincronicen las lecturas del suelo, para garantizar la continuidad del registro en zonas con conectividad intermitente. |

## 3.2. Impact Mapping

En esta sección se presenta el Impact Mapping de OsoSense, el cual permite alinear los objetivos estratégicos del proyecto con las funcionalidades técnicas desarrolladas. Siguiendo la metodología de cinco niveles, cada mapa nace de un Objetivo de Negocio (Why), identifica a los actores clave (Who), define el impacto o cambio de comportamiento necesario (How), establece los entregables técnicos (What) y los desglosa en Historias de Usuario (User Stories).

Se han desarrollado tres mapas de impacto correspondientes a los tres objetivos principales del producto:

#### Impact Map 1: Adopción Tecnológica y Monitoreo Continuo

**Business Goal 1 (WHY):** Lograr la adopción activa de la plataforma OsoSense en 50 parcelas agrícolas en la costa norte del Perú durante los primeros seis meses tras el lanzamiento, validando la viabilidad del monitoreo continuo.

*   **Persona (WHO): Diego Ramos (Productor)**
    *   **Impact (HOW):** Reducir la incertidumbre y monitorear el suelo a distancia, abandonando las decisiones empíricas y gastos a ciegas.
    *   **Deliverables (WHAT):** Dispositivo IoT de campo con servicio de borde.
        *   *User Story:* Como productor agrícola, quiero que el dispositivo lea automáticamente la conductividad eléctrica y humedad para no tener que medirlas manualmente.
        *   *User Story:* Como productor agrícola, quiero que los datos se guarden localmente cuando no hay internet y se sincronicen después para no perder mi historial.

*   **Persona (WHO): María Fernanda Salazar (Asesora Técnica)**
    *   **Impact (HOW):** Agilizar la consulta remota del estado de las parcelas de sus clientes para recomendar el uso de la plataforma.
    *   **Deliverables (WHAT):** Dashboard móvil simplificado.
        *   *User Story:* Como asesora técnica, quiero ver el estado actual de la parcela desde mi celular para saber si debo agendar una visita urgente a mi cliente.
